## 1. Resumo Executivo

### 1.1 O que é o Nexly?

O **Nexly** é uma plataforma **SaaS multi-tenant** de gestão para pequenos negócios —
salões de beleza, clínicas de estética, barbearias, petshops e estúdios. O sistema
resolve o problema da **fragmentação operacional** entre agenda de serviços e controle
de estoque físico, unificando ambos em um único produto com login multi-empresa.

O **diferencial central** é a **baixa automática de insumos do estoque** quando um
serviço agendado é concluído — eliminando o retrabalho manual do operador e recuperando
a lucratividade perdida por falta de visibilidade do custo real de cada atendimento.

### 2.2 Fluxo de autenticação

```
[Cliente]                    [API]                         [DB/Redis]
   │                           │                              │
   │ POST /auth/login          │                              │
   │ {email, senha}            │                              │

   │                           │ 1. Rate limit (Redis)       │
   │                           │ 2. Busca usuario (DB)       │
   │                           │ 3. Verifica Argon2id         │
   │                           │ 4. Gera JWT RS256 (15 min)  │
   │                           │ 5. Gera refresh token (7 d) │
   │                           │ 6. Salva refresh (DB + Red) │
   │     {accessToken,         │                              │
   │      usuario} + cookie    │                              │
   │◄──────────────────────────│                              │
   │                           │                              │
   │ [Requisição autenticada]  │                              │
   │ Authorization: Bearer xxx │                              │
   │──────────────────────────►│                              │
   │                           │ AuthGuard → valida JWT       │
   │                           │ TenantInterceptor → ALS.run  │
   │                           │ Prisma Extension → injeta    │
   │                           │   empresaId em queries       │
   │                           │ RLS → valida no banco        │
```

### 2.3 Isolamento multi-tenant (defesa em profundidade)

**Camada 1 — Aplicação (Prisma Extension):** `tenant-extension.ts` intercepta
todas as queries (`findMany`, `findFirst`, `create`, `update`, `delete`, `count`,
`upsert`) e injeta `empresaId` do `AsyncLocalStorage`.

**Camada 2 — Banco (Row-Level Security):** `seed-rls.sql` habilita RLS em 9 tabelas
via função `app_current_tenant()` e policies `tenant_isolation` com
`USING (empresa_id = app_current_tenant())`. Tabelas sem RLS: `empresas`,
`usuarios`, `refresh_tokens`, `_prisma_migrations`.

### 2.4 Fluxo de baixa automática de estoque (diferencial central)

```
[Agendamento concluído]
        │
        ▼
AgendamentosService.atualizarStatus(id, CONCLUIDO)
        │
        ▼
eventEmitter.emit('agendamento.concluido', {agendamentoId, servicoId})
        │
        ▼
EstoqueIntegracaoService (listener @OnEvent)
        │
        ├─► Busca insumos do serviço (insumoServico)
        ├─► Para cada insumo:
        │     └─► estoqueService.registrarSaidaTx(produtoId, qtd, motivo, agendamentoId)
        │           ├─► updateMany com WHERE estoqueAtual >= quantidade
        │           ├─► Se count === 0 → lança OUT_OF_STOCK (409)
        │           └─► Cria MovimentacaoEstoque (SAIDA)
        └─► Tudo dentro de $transaction (atômico)
```

## 7. Segurança

### 7.1 Checklist OWASP Top 10 mitigado

| Vulnerabilidade | Mitigação |
|---|---|
| **Broken Access Control** | RLS + Prisma Extension + AuthGuard + RolesGuard |
| **Cryptographic Failures** | JWT RS256 (2048 bits), Argon2id, HTTPS em prod |
| **Injection** | Prisma (query parameterizada), Zod (validação de entrada) |
| **Insecure Design** | Rate limit, refresh rotation, soft-delete |
| **Security Misconfiguration** | Env validation (Zod), CORS explícito, Helmet |
| **Identification Failures** | JWT + refresh cookie httpOnly, 5 falhas/15 min |
| **Software Integrity** | Package lock, Docker pinned versions |
| **Logging & Monitoring** | LoggingInterceptor, X-Request-Id, logs estruturados |
| **SSRF** | N/A (não faz requisições externas arbitrárias) |
| **Secretos em código** | `.env` + `.pem` no `.gitignore`, chaves em base64 |

### 7.2 Pontos de atenção (a melhorar)

### 11.1 Dashboard financeiro consolidado (CMV) 🔴 P1

**Complexidade:** ⭐⭐ (3-4 dias) | **Impacto TCC:** ⭐⭐⭐⭐⭐ (diferencial de BI)

### 11.2 Lembrete automático de agendamento 🔴 P1

**Problema:** No-show (falta sem aviso) gera perda de receita. Salões perdem
em média 15-20% dos agendamentos por no-show.

**Solução:**
- Job agendado via `@nestjs/schedule` (cron: 18h todo dia)
- Verifica agendamentos de amanhã com status AGENDADO
- Envia e-mail de lembrete via Nodemailer (SMTP configurável)
- Template: "Olá {cliente}, você tem {serviço} amanhã às {hora} com {profissional}"
- Configurável: enviar X horas antes, template personalizado
- Log de envios na tabela `lembretes_enviados`

**Complexidade:** ⭐⭐⭐ (4-5 dias) | **Impacto TCC:** ⭐⭐⭐⭐ (diferencial engajamento)

### 11.3 Leitor de código de barras 🟡 P2

**Problema:** Operador do PDV digita nome/SKU manualmente. Com dezenas de
produtos, isso é lento e propenso a erro.

**Solução:**
- Usar `navigator.mediaDevices.getUserMedia()` + `@zxing/library` (leitura via câmera)
- Botão de scanner (ícone de câmera) ao lado do campo de busca no PDV
- Ao detectar código de barras → busca produto por SKU → adiciona ao carrinho
- Compatível com leitores físicos (modo HID — digitação automática)
- Feedback visual: borda verde piscando ao detectar

**Complexidade:** ⭐⭐⭐ (3-4 dias) | **Impacto TCC:** ⭐⭐⭐⭐⭐ (diferencial técnico)

### 11.4 Cálculo de comissão de profissionais 🟡 P2

**Problema:** Salões pagam comissão variável. Hoje é calculado manualmente.

**Solução:**
- Campo `comissaoPercentual` (decimal 0-100) no modelo `Profissional`
- Campo `comissaoFixa` (decimal opcional) no modelo `Servico`
- Relatório: `GET /relatorios/comissoes?mes=8&ano=2026`
- Retorna: por profissional → total de serviços, valor total, comissão devida
- Total geral a pagar no mês

**Complexidade:** ⭐⭐ (2-3 dias) | **Impacto TCC:** ⭐⭐⭐ (médio)

### 11.5 Controle de vencimento de produtos 🟡 P2

**Problema:** Produtos de beleza têm prazo de validade. Sem controle, há perda.

**Solução:**
- Campo `dataValidade` (Date?) no modelo `Produto`

- Alerta no dashboard: "Produtos vencendo este mês"
- Relatório: `GET /relatorios/vencimentos?dias=30`
- Sugestão: baixar automaticamente produtos vencidos (movimentação PERDA)

**Complexidade:** ⭐⭐⭐ (3-4 dias) | **Impacto TCC:** ⭐⭐⭐ (médio)

## 15. Lições Aprendidas

### 15.1 Técnicas

1. **Prisma Extension + RLS** é defesa em profundidade — o extension cobre
   queries que o RLS não alcança (ex: dentro de transactions com `tx`).

2. **`AsyncLocalStorage` é frágil** — se um interceptor rodar na ordem errada,
   o contexto de tenant fica vazio e tudo falha com 401.

3. **`npx ts-node` não carrega `.env`** — custou horas debugando o seed que
   rodava e não inseria nada. Solução: `--require dotenv/config`.

4. **Node 24 strict** quebrou resolução de módulos sem extensão.
   O `@nexly/shared` com `main: ./src/index.ts` precisou ser compilado.

5. **Winget** é excelente para dependências nativas. Redis + PostgreSQL
   instalados em segundos, sem interface gráfica.

### 15.2 Processo

1. **Commits atômicos e descritivos** — cada push é independente.
2. **Testes antes do deploy** — 93 testes pegaram bugs que apareceriam em produção.
3. **Documentação viva** — `docs/` cresceu junto com o código.

### 15.3 Produto

1. **Dark mode é produtivo** — `zinc-900` como base, tudo deriva naturalmente.
2. **Empty states transformam** — o PDV ficou profissional após as mensagens.
3. **Seed realista é essencial** — 82 registros fazem parecer produção real.
